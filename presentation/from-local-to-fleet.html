Solving the "Works on My Machine" Problem with Docker

  • Docker packages code, libraries, and config into one portable unit
  • Same artifact runs on your laptop, CI, staging, and production
Open with the pain everyone knows. Docker is not just virtualization — it's a packaging and delivery standard.

"It Works on My Machine"

  • The conflict — Node/Python versions, missing libs, OS differences between dev and prod
  • The cost — hours lost debugging environment mismatch and failed deploys
  • The solution — Docker runs the app identically on any host that has the engine
Keep it relatable. The fix is reproducible environments, not better documentation of dependencies.

Blueprints vs. Living Instances

  • Image — read-only template (Class): app + runtime + deps
  • Container — running, isolated instance (Object)
Pull→ Build→ Push

Download from a registry · Create locally · Share with your team

OOP analogy lands quickly. Pull from Docker Hub, build from a Dockerfile, push to your registry.

Why Containers are Lightweight

VMs Containers ┌─────────┐ ┌─────┐ ┌─────┐ ┌─────┐ │ Guest OS│ each VM │ App │ │ App │ │ App │ ├─────────┤ └──┬──┘ └──┬──┘ └──┬──┘ │ App │ └──┬───┴───┬───┘ └────┬────┘ Container Runtime │ │ ─────┴────────────────────────── Host OS Kernel (shared) Hypervisor · GBs · minutes boot · MBs · ms start
  • VMs — full guest OS per machine; heavy, slow
  • Containers — share the host kernel; fast and dense
Containers isolate processes, not hardware. You get many more workloads per host.

How Docker Works

  • Client — CLI you type into (docker run, docker buildx)
  • Daemon (dockerd) — background service managing images, containers, networks
  • Registry — image store & share (Docker Hub, GHCR, private registries)
You ──docker CLI──▶ dockerd ──pull/push──▶ Registry └── creates ──▶ Containers
Client talks to daemon via API socket. Workshop Module 0 installs and verifies the daemon.

Modules 1–2: The First Container

Workshop: examples/hello-docker/

docker buildx build --load -t hello-docker:1.0 .
docker run -d --name hello -p 8080:80 hello-docker:1.0
  • Build — Dockerfile layers a custom page onto nginx:alpine
  • Port mapping — host 8080 → container 80
  • Verify — open localhost:8080 or curl localhost:8080
Workshop uses Buildx with --load. Tag hello-docker:1.0 matches WORKSHOP.md exactly.

Modules 2–4: Inside & Manage

docker exec -it hello sh      # explore (Alpine shell)
docker logs hello               # inspect output
docker ps / docker ps -a        # list containers
docker stop hello && docker rm -f hello
docker rmi hello-docker:1.0     # remove image
  • Exec — run commands inside a live container
  • Housekeeping — stop, remove containers; prune images when done
  • Optional (Module 3) — docker commit snapshots a container to a new image
nginx:alpine uses sh, not bash. Module 4 covers stop/start/rm/rmi lifecycle. Commit is optional in the workshop.

Module 5: Multi-Container Stacks

Workshop: examples/compose-demo/ · port 8081

cd examples/compose-demo
docker compose up -d --build --wait
  • Docker Compose — entire stack (web + API + Redis) in one YAML file
  • Bridge networks — frontend and backend isolate service traffic
  • Test — curl localhost:8081/api/health (hits increment via Redis)
Compose v2: docker compose (space), not docker-compose. Tear down with docker compose down --volumes.

Security First with Podman

  • The risk — Docker's central daemon often runs as root; broader attack surface
  • Podman — daemonless, rootless; containers are child processes of the user
  • Advantage — deep systemd integration on Linux for unit-managed containers
Podman is CLI-compatible with Docker for many workflows. Good option when rootless security is a requirement.

Managing Fleets with Kubernetes

  • Concept — orchestrate containers across a cluster of machines, not one host
  • Self-healing — restarts failed pods, reschedules onto healthy nodes
  • Auto-scaling — scales replicas with CPU, memory, or custom metrics
  • When to use what — Compose for local dev · Kubernetes for production fleets
