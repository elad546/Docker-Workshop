Why containers?

Set the problem: dev laptops differ from production. Containers package app + dependencies into a portable unit.

VMs vs containers

Containers share the host kernel — lighter and faster to start than full VMs. Docker is the tool we'll install in Module 0.

Core concepts

Image

Read-only template — filesystem + metadata. Built from a Dockerfile.

Container

Running (or stopped) instance of an image. Isolated process with its own filesystem layer.

Analogy: image = class, container = object instance

Keep this short — they'll feel these concepts in Module 1–2. Emphasize layers/cache when building in Module 1.

Module 0 5–10 min

Prerequisites — install & verify Docker

  • docker.io — Docker Engine
  • docker-buildx — modern build tool
  • docker compose — Compose v2 (space, not hyphen!)
NOW: Participants run Module 0 cells in order: Install Docker → Install Compose → Enable service → Verify.
Module 0 is the slowest for many groups. Walk the room while apt runs. Two common failures: permission denied on socket, and compose not found.

Module 0 — Troubleshooting

Permission denied

sudo chown $USER /var/run/docker.sock

Then re-run Docker daemon info

Compose not found

Re-run Install Compose v2 plugin.
Must show docker compose version v2.x.
Module 5 will fail without this.

Do not advance to Module 1 until docker info and docker compose version both succeed.
Optional permanent fix: usermod -aG docker $USER (requires re-login). For workshop, chown is faster.

Module 1 5–7 min

Creating an image

Explore examples/hello-docker/

FROM nginx:alpine
COPY app/index.html /usr/share/nginx/html/index.html
  • docker buildx create --use — set up builder
  • docker buildx build --load -t hello-docker:1.0 .
  • Each instruction = a cached layer
NOW: Run Set up Buildx builder → Build hello-docker image → List hello-docker images.
Point out the Dockerfile is tiny — FROM base image, COPY one file. Build output shows layer steps. Tag `-t hello-docker:1.0` names the image for later modules.

Module 2 8–10 min

Run & exec

docker run -d --name hello -p 8080:80 hello-docker:1.0
FlagMeaning
-dDetached (background)
--name helloHuman-readable name
-p 8080:80Host port → container port
NOW: Run container → docker ps → curl localhost:8080.
Explain port mapping: localhost:8080 on host reaches nginx port 80 inside container. curl should return "Hello from Docker!" HTML.

Module 2 — Exec & logs

Non-interactive exec

docker exec hello cat \
  /usr/share/nginx/html/index.html

Interactive shell

docker exec -it hello sh

Try hostname, ls, then exit

docker logs hello
NOW: Exec cells + interactive shell + logs. Give ~2 min for interactive shell exploration.
Interactive shell is a good moment for participants to explore. `-it` = interactive + TTY. logs shows nginx access log entries from their curl requests.

Module 3 optional · 5 min

Commit a container to a new image

docker exec hello sh -c 'echo "committed-layer" > /tmp/marker'
docker commit hello hello-docker:committed
docker run --rm hello-docker:committed cat /tmp/marker

docker commit snapshots the container filesystem — useful for debugging, but prefer Dockerfile for reproducible builds.

NOW: Expand "Module 3" in WORKSHOP.md and run the commit cells — or skip if short on time.
Optional section is collapsed in WORKSHOP.md under details/summary. Skip entirely if behind schedule.

Module 4 5–7 min

Container & image management

docker stop hello      # graceful stop
docker start hello     # restart stopped container
docker rm -f hello     # remove container
docker rmi hello-docker:1.0   # remove image
  • docker ps — running  |  docker ps -a — all
  • Must remove container before removing its image
  • docker image prune -f — optional cleanup
NOW: Stop → start → rm → rmi sequence. Container must be removed before image.
Common error: can't rmi while container exists. rm -f removes running or stopped containers.

Module 5 10–12 min

Docker Compose + bridge networks

Multi-container app in examples/compose-demo/

  • web — nginx reverse proxy (host port 8081)
  • api — Python health API, talks to Redis
  • redis — hit counter backend only
Compose orchestrates multiple services from one YAML file. Bridge networks isolate traffic — api bridges frontend+backend, redis only on backend.

Module 5 — Compose file

networks:
  frontend: { driver: bridge }
  backend:  { driver: bridge }

services:
  web:   ports: ["8081:80"]   networks: [frontend]
  api:   networks: [frontend, backend]
  redis: networks: [backend]
NOW: docker compose config → docker network ls → docker compose up -d --build --wait
`docker compose config` validates YAML. `--wait` waits for healthchecks (api has one). First build may take a few minutes — good time for Q&A.

Module 5 — Test the stack

curl -s localhost:8081          # web front-end
curl -s localhost:8081/api/health   # proxied API

Run the health curl several times — redis_hits should increment.

{"status":"ok","hostname":"…","redis_hits":3}
NOW: curl web + API health (repeat API curl). Then docker compose ps and inspect networks.
nginx proxies /api/ to api:5000 internally — participants can't curl api directly from host (no published port). That's the point of the network segmentation demo.

Module 5 — Tear down

cd examples/compose-demo
docker compose down --volumes --remove-orphans
  • down stops and removes containers + networks
  • --volumes removes named/anonymous volumes
  • --remove-orphans cleans leftover containers
NOW: Tear down compose stack before Module 6 cleanup.
Verify with docker network ls — compose-demo networks should be gone.
